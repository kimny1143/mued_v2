# C8 — 他店販売のシリアル引き換え設計（masterchain・設計のみ）

*mued 起草 / 2026-09-28 / 依頼＝conductor（kimny 2026-09-28 裁定・Chief 中継）/ ★設計のみ。実装の可否と順序は、この設計を conductor が読んでから決める。発売経路（EULA・live env・購入ボタン）の作業が優先。*

## 0. 前提（kimny 裁定・方針 B）

- **価格:** 定価 $69 のみ。割引なし。
- **売り場:** Plugin Boutique（PB）、KVR Marketplace（KVR）、ADSR にも同じ定価で並べる。kimny 逐語「Bの方針で、PB及びKVR ADSRにも同じタイミングて載せるべきでは？」
- **鍵の受け取り:** mued.jp のポータルに統一する。他店で買った客のメールもここで取る。
- **発売:** 店は発売の gate にしない。発売は直販と KVR から出し、他の店は承認が下りた日に追加する。

**この設計が変えないもの:**
- 鍵の形式と署名。形式は v2（`lib/masterchain/license.ts`）、署名鍵は K1（`MASTERCHAIN_LICENSE_PRIVATE_KEY`）。
- プラグイン側の検証器（dsp `LicenseVerifier.h`）。

§1.4 で示すとおり、プラグインの変更は不要。

## 1. 仕組み — 店ごとのシリアル → ポータルで引き換え → LICENSED 鍵

### 1.1 シリアルの 2 つの形（どちらでも受ける）

| 形 | 誰が作るか | こちらが持つもの | 使う場面 |
|---|---|---|---|
| **(A) 店が支給** | 店が自前のシリアルを発番し、一覧をこちらへ渡す | 一覧を取り込んだ**ハッシュ**（平文は保存しない） | 店のシステムが自前発番しかできない場合 |
| **(B) こちらが pool を渡す** | こちらが発番し、CSV で店に渡す（店はそれを 1 本ずつ客に配る） | 発番した**ハッシュ**のみ。平文の CSV は渡した後に消す | 店が「開発者のシリアル一覧を配る」方式の場合 |

**同じ表で受ける。** 行の出所は `origin = 'store_supplied' | 'we_issued'` の列で区別し、引き換えの処理は 1 本にする。

- **(B) の書式:** `MC-<店>-XXXX-XXXX-XXXX-C`。
  - 本体は Crockford base32 で、`crypto.randomBytes` から 60 bit 以上を取る。
  - 末尾の `C` はチェック文字で、DB を引く前に打ち間違いを弾く。
  - 60 bit あれば総当たりは現実的でない（§1.5 の回数制限は保険）。
- **(A) の書式は店次第。** 店ごとに正規化の関数を 1 つ持つ（大文字化・空白とハイフンの除去）。正規化した後でハッシュする。
  - エントロピーは店の発番に依存するので、(A) では回数制限の比重が上がる。
- **ハッシュ:** `sha256(<店>:<正規化したシリアル>)`。店を混ぜるので、別の店に同じ文字列があっても衝突しない。
  - 平文を持たないため、DB が漏れても使えるシリアルは出ない。
  - 客が同じシリアルを入れ直した時は、同じハッシュで引ける。

### 1.2 表（純粋追加・Tier 2 の migration）

**新表 `masterchain_store_serials`:**

| 列 | 型 | 意味 |
|---|---|---|
| `id` | uuid PK | |
| `channel` | text not null | `'kvr' \| 'pb' \| 'adsr' \| …`。店の一覧は registry の定数から作る（§2.2） |
| `batch_id` | text not null | 取り込みまたは発番の単位。漏洩時に束ごと無効にするため |
| `origin` | text not null | `'store_supplied' \| 'we_issued'` |
| `code_hash` | text not null **unique** | §1.1 のハッシュ |
| `status` | text not null | `'available' \| 'redeemed' \| 'void'` |
| `redeemed_purchase_id` | uuid null → `masterchain_purchases.id` | 引き換えで作った購入行 |
| `redeemed_at` | timestamptz null | |
| `voided_at` / `void_reason` | timestamptz / text null | `'refund' \| 'leak' \| 'store_recall'` |
| `created_at` | timestamptz not null | |

**既存 `masterchain_purchases` への追加（どちらも nullable または default 付きで、純粋追加）:**
- `channel text not null default 'direct'`。既存の行は直販なので、default のままで正しい。
- `refunded_at timestamptz null`。返金の事実の記録で、直販と他店の両方で使う（§1.6）。

**他店の購入行の埋め方:**
- `order_id` = `<店>:<serial の id>`。unique が効くので、1 シリアルにつき 1 行になる。
- `email` = 引き換えた人の**確認済み**メール。
- `amount_cents` / `currency` / `buyer_country` = **null**。
  - 他店の売値・税・国はこちらに届かない。値の正本は店の明細。
  - この列はもともと「購入者が払った総額」で、当社の売上ではない（schema の注記を参照）。null は「測れていない」の意味で、0 にはしない。

### 1.3 引き換えの流れ

入口はポータル（`/dashboard/plugins`）に置く「シリアルを引き換える」欄。API は `POST /api/masterchain/redeem`。

1. **認証:** Clerk のセッションが必須で、**確認済みメールだけ**を持ち主とする。境界は `lib/plugins/portal-data.ts` と同じで、client が送ったメールは信用しない。
   - ポータルは passwordless なので、他店の客も、メールのコードでそのまま入れる。
2. **入力:** シリアルと EULA 同意（チェック + `EULA_VERSION`）。
   - **他店の客について EULA 同意を記録できる場所はここしかない。** 店の checkout はこちらの `eula_version` tag を運ばない。
3. **検査（1 つの transaction の中）:**
   1. 正規化する。(B) はチェック文字も見て、合わなければ DB を引かずに「打ち間違い」と返す。
   2. ハッシュを取り、`SELECT … FOR UPDATE` で行をロックする。同時に 2 回押されても 1 回しか通らない。
   3. 状態で分岐する。

      | 状態 | 応答 |
      |---|---|
      | 行が無い | 汎用の「無効なシリアル」。失敗回数を加算（§1.5） |
      | `void` | 「このシリアルは使えません。サポートへ」 |
      | `redeemed` で、購入行の email が呼び手の確認済みメールに含まれる | **同じ鍵を返す**（冪等。新しく発行しない） |
      | `redeemed` で、別の人 | 「すでに使われています。サポートへ」。持ち主のメールは出さない |
      | `available` | 次の 4 へ |
4. **発行:**
   - `issueLicense({ owner: 確認済みメール, order: '<店>:<serial の id>' })` を呼ぶ。直販と同じ関数・同じ K1・同じ scope。
   - 購入行を insert し、シリアルを `redeemed` にして commit する。
5. **渡す:** 画面にその場で鍵を出す（ポータルの購入一覧にも、同じメールで自動的に載る）。そのうえで、直販と同じ `sendMasterchainLicenseDelivery` で鍵のメールを送る。
   - **ここは直販と失敗の扱いを変える。** 直販は webhook なので、失敗は **fail-closed** にして FastSpring の再送に任せる。
   - 引き換えは本人がその場に居て、鍵はポータルに載っている。だからメールの失敗は **commit 後の error log** にし、画面に「メールが届かなくてもこのページから取れます」と出す。
   - メールの失敗で引き換えを rollback すると、次の再試行は「すでに使われています」に当たってしまう。

### 1.4 プラグイン側は変わらない（確認済み）

- dsp の `LicenseVerifier.h` が見るのは次の 3 つだけ。
  - 署名
  - `product=MUEDsp` と `scope=masterchain`
  - `expires_at`
- `order=` と `owner=` は**中身を解釈しない**。重複行の検査だけがかかる。
- よって `order=kvr:<uuid>` の鍵は、直販の鍵と同じく `Licensed` になる。
- 注意は発行側に 1 つだけ。検証器が重複行を弾く理由は、値に改行を混ぜた行の注入なので、**`order` と `owner` に改行が入らないこと**を発行側で保証する。
  - uuid と確認済みメールは改行を含まない。発行関数の既存の検査もそのまま効く。

### 1.5 総当たり・乱用

- 失敗は、確認済みユーザーごとと IP ごとに数える。上限の例は 10 回/時で、超えたら一時停止する。
  - 仕組みは既存の `lib/middleware/rate-limit.ts` の `checkRateLimit` を使う。
- 成功は 1 ユーザーあたり 1 日 N 本の上限を置く。1 人が大量に引き換えるのは転売や漏洩の兆候なので、超えたら止めて log に 1 行出す。
- 応答の文面は「無い」「void」「他人が使用済み」で分けるが、どれも持ち主の情報は出さない。

### 1.5b 引き換えで取るメールの用途（KVR Seller Policy・2026-09-28 conductor 確認）

- **ポータルで取るメールは、鍵の発行とサポートにだけ使う。** ニュースレターの登録は別のチェックにし、既定は off（明示の opt-in）。KVR の規約では、買い手の情報は注文の処理と客対応にだけ使え、メール配信には明示の同意が要る。
- **KVR の客に見せる引き換えの画面には、直販の購入へ誘導する文言を出さない。** 規約の non-interference 条項（「KVR と競合する第三者のサービスの利用を勧めない」「手数料を避けるため KVR の外で取引を完了しない」）に当たるため。ポータルはここでは鍵の引き換えにだけ使う。

### 1.6 重複・再利用・返金

| 事象 | 扱い |
|---|---|
| **同じ人が 2 回入れる** | 同じ鍵を返す（§1.3 の 3）。新しい鍵は出さない（直販の「発行は注文ごとに 1 回」と同じ） |
| **別の人が同じシリアルを入れる**（譲渡・打ち間違いの一致・漏洩） | 先着が持つ。後の人はサポートへ。サポートで付け替える時は、旧購入行に `refunded_at` を付けずに**新しい行を作る手作業**になる。旧鍵はオフライン検証なので取り消せない |
| **漏洩**（束がネットに流れた） | 未使用の残りを `batch_id` ごと `void`（`leak`）にし、店に差し替えの束を頼む。使われた分は取り消せない。1 シリアルにつき 1 鍵なので、被害は使われた本数で頭打ちになる |
| **店での返金**（未引き換え） | シリアルを `void`（`refund`）にする。以後は引き換えられない |
| **店での返金**（引き換え済み） | 購入行に `refunded_at` を付ける。**鍵は取り消せない**（オフライン検証・DRM なし＝Q2(a) の前提）。直販の返金も同じで、今の直販にも返金を取り消す経路は無い |
| **返金の知らせが引き換えより後に来る** | 上と同じ。取り消せないことを受け入れ、`refunded_at` で分母から外せるようにする |

**返金方針は売り手が決めてよいが、商品ページに明記が要る**（KVR の規約の本文は「all sales final」）。直販と同じ方針を各店の商品ページに書く。

**返金の知らせの経路は店次第**（§4 の分岐）。API や webhook があれば自動にし、無ければ月次明細の CSV を取り込む script（Tier 2・admin のみ）にする。

## 2. 計測 — 引き換えの実数を店ごと・日ごとに

### 2.1 何を数えるか

- **正本は `masterchain_purchases`。** 直販の行は購入時、他店の行は引き換え時にでき、どちらにも `channel` がある。
- 「売れた本数」と「引き換えた本数」は**別の数**なので、混ぜない。
  - 売れた本数は店の明細（月次・手で入る）。
  - 引き換えた本数はこちらの DB（日次・自動）。
  - 90 日判定の分母に使うのは**引き換えの実数＋直販**。
  - 店の「売れたが未引き換え」は分母に入らない。こちらで観測できないからで、差は店の明細と突き合わせて別に見る。
- **返金の扱い:** `refunded_at` のある行は数え方を分ける。`gross`（引き換え・購入の全数）と `net`（返金を除く）を並べ、割り算はしない。

### 2.2 funnel-numbers の key 案

```json
"masterchain_licenses": {
  "cumulative": { "direct": 0, "kvr": 0, "pb": 0, "adsr": 0, "total": 0 },
  "cumulative_net": { "direct": 0, "kvr": 0, "pb": 0, "adsr": 0, "total": 0 },
  "day_utc": { "direct": 0, "kvr": 0, "pb": 0, "adsr": 0, "total": 0 },
  "definition": "…"
}
```

- **店の列は registry の定数から zero-fill で作る。** 手書きの key にしない。MUEDrive が「集計側の手書き 2 key」のせいで 0 に数えられた前例（`scripts/aggregate-plugin-funnel-daily.ts` の注記）と同じ穴を塞ぐため。
- `day_utc` はレポート全体と同じ UTC の日。直販は `created_at`、他店は `redeemed_at` を使う（購入行の `created_at` は引き換え時と一致する）。
- **取得に失敗したら `null`＋anomalies に 1 行。0 にしない。** funnel-numbers の既存の規則どおり、率は出さない。
- **本番の前提（kimny の手）:** collector の read-only ロール `funnel_collector_ro` には、今 `plugin_entitlements` の SELECT しかない（`docs/ops/collector-readonly-role.md`）。この key を出すには `GRANT SELECT ON public.masterchain_purchases TO funnel_collector_ro;` が要る。
  - 本番 DB の操作なので、kimny の実行になる。
  - 列を絞るなら、`email` と `license_key` を含まない view を作ってそこに GRANT する方が least privilege に合う。推奨はこちら。

## 4. 店の契約で決まる 3 点と分岐

契約の中身は kimny が確かめる（外部契約）。**どの答えが来ても通るように、分岐の点をここに固定する。**

### 4.1 手数料

- **システムへの影響はない。** 売値は $69 固定で、手数料は店の取り分。当社の純額は店の明細にしか出ない（DB の `amount_cents` は他店では null）。
- 影響が出るのは原価率と、店ごとの純額の比較。値は DB に焼かず、明細を正本にする。

### 4.2 価格を縛る条項

| 契約の形 | 分岐 |
|---|---|
| 定価で出せる・割引の参加は任意 | そのまま載せる |
| **セールへの参加が義務**、または店が勝手に値引きできる | **方針 B（割引しない）と衝突する** → その店には載せない。店は発売の gate ではないので、載せないことで発売は止まらない |
| **最恵待遇（MFN / 価格の同一）** | 方針 B は全店同じ定価なので、今は衝突しない。ただし将来直販だけ値を動かす時に縛りになる → conductor / kimny の判断に上げる |

どの場合もシステムの変更は要らない。

### 4.3 シリアルをこちらのポータルで引き換えさせてよいか

| 契約の形 | 分岐 |
|---|---|
| **よい**（店がシリアルを配り、利用者は開発者のサイトで登録） | 本設計そのまま（§1）。(A)/(B) は店の方式に合わせる |
| **よいが、アカウント作成の強制は不可** | ポータルはメールのコードで入れる passwordless なので、アカウント作成を求めずに済む。文面は「メールで確認」とし、登録という語を出さない |
| **不可**（鍵は店の中で渡し切る必要がある） | **最後の手段 (C): 署名済みの鍵ファイルを事前に作って店に渡す。** `owner=` に束の名を入れる。検証器は owner を解釈しないので、鍵としては動く。**ただしメールは取れない**（「受け取りをポータルに統一」に反する）うえ、漏れた鍵は取り消せない。→ kimny の判断に上げる。推奨は**その店には載せない** |

**もう 1 つ、契約で決まる実務の点:** 返金の知らせ方（API / webhook / 月次明細）。これで §1.6 の自動・手動が決まる。

### 4.4 KVR の確定事項（Seller Policy・2026-09-28 conductor が管理画面で確認）

- **注文の処理（鍵・binary）は売り手の責任で、KVR は店の側でシリアルを作らない。** → **KVR は (B) こちらの pool を渡す形**で、§4.3 の「よい」の行に当たる。
- 買い手の情報の用途と、ポータルでの直販誘導の禁止 → §1.5b。
- 返金方針は商品ページに明記 → §1.6。

## 5. 順序と Tier（実装する場合）

1. **migration**（新表・2 列追加）: 純粋追加なので Tier 2。本番への適用は kimny（コードの merge より前）。
2. **発番・取り込みの script**（(B) の発番と CSV 出力・(A) の取り込み・`void` の一括）: Tier 2、admin のみ。平文の CSV は scratch に出して渡した後に消す。
3. **引き換えの API とポータルの欄:** ライセンス鍵を発行する入口が増える＝**認証・セキュリティに当たるので Tier 3（conductor）**。
4. **計測 key（§2.2）:** Tier 2。**前提は本番の GRANT（kimny）。**
5. **発売の日に要るのは KVR の分だけ。** 他の店は承認が下りた日に、その店の `channel` と束を足すだけで済むようにしておく（コードの変更なし）。

## 6. 未確定の点（この設計では決めない）

- PB / ADSR それぞれのシリアルの方式（(A) か (B) か）と、3 店の返金の知らせ方（KVR の方式は (B) で確定・§4.4）。契約と店の資料による（kimny の窓口）。
- 引き換え 1 日あたりの上限 N と、失敗回数の上限の値。
- `masterchain_redeem` を GA4 の key event にするか（insight課 の計測規約に合わせる）。
- 鍵のメールの文面を他店向けに分けるか（「〜でのご購入ありがとうございます」）。copy は content課 → mued の分担による。
