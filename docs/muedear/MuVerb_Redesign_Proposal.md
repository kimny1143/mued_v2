# MuVerb リデザイン提案書

## 現状の問題

### 現行仕様
- ゲーム形式：「今かかっているリバーブはどのタイプ？」（1音聴いて種類を同定）
- 選択肢：Hall / Room / Plate など
- 実装：IR（インパルスレスポンス）ベース、ConvolverNode

### 問題点
- **スマホ環境ではリバーブの種類差がほとんど判別できない**
- イヤホンでもスピーカーでも、Hall vs Room の空間差は微妙すぎる
- リファレンスなしで種類を同定するのは、モニター環境でもかなり高難度
- 唯一 Spring くらい派手に違うものしか判別できない
- 結果として「当てずっぽうゲーム」になってしまい、学習効果が薄い

---

## リデザイン方針

### コンセプト転換

| | 現行 | 提案 |
|--|------|------|
| 形式 | 1音聴いて種類を同定 | **A/B比較で種類を判別** |
| 問い | 「これは何リバーブ？」 | **「Plateはどっち？」** |
| 認知負荷 | 高（絶対評価） | 低（相対評価） |
| スマホ適性 | ✕ | ○ |

### 設計原則
- **MuComp / MuFreQ と同じ A/B 2択フォーマットに統一**
- 「比較」させることで、スマホでも判別可能な難易度に落とす
- 特徴が際立つペアを出題し、学習効果を最大化

---

## ゲーム設計

### 基本フロー
1. 同じ音源に異なるリバーブを2つかける（A / B）
2. 「Plateはどっち？」と問う
3. A または B を選択
4. 正解／不正解 → フィードバック

### 出題ペア設計

特徴差が大きいペアから段階的に難易度を上げる。

#### Level 1（Easy）— 明確に違うペア
| ペア | 判別ポイント |
|------|-------------|
| Plate vs Hall | 金属的な響き vs 広がり感 |
| Spring vs Room | バネ感（ビヨン） vs 自然な部屋鳴り |
| Plate vs Spring | 滑らかな金属感 vs 明確なバネ音 |

#### Level 2（Medium）— やや近いペア
| ペア | 判別ポイント |
|------|-------------|
| Hall vs Room | ディケイの長さ、空間の広さ |
| Plate vs Chamber | 金属的 vs 石壁の反射 |
| Room vs Ambience | 部屋鳴り vs 短い初期反射のみ |

#### Level 3（Hard）— 近い特性のペア
| ペア | 判別ポイント |
|------|-------------|
| Large Hall vs Medium Hall | ディケイの微妙な長さの差 |
| Small Room vs Chamber | 空間サイズの微差 |
| Plate vs Shimmer | 金属的 vs 金属的＋倍音 |

### 出題テキスト例
- 「Plateはどっち？」
- 「Springはどっち？」
- 「Hallはどっち？」
- 「より広い空間はどっち？」（Level 3 応用）

## 技術仕様

### Phase 1: IR版（現行エンジン流用）

- **変更点は出題ロジックとUIのみ、DSP側の変更なし**
- 既存のConvolverNode + IR素材をそのまま使用
- A/B それぞれに異なるIRを適用して再生
- MuComp と同じ再生UIコンポーネントを流用

#### 必要なIR素材
| タイプ | 特徴 | 入手 |
|--------|------|------|
| Plate | 金属板の共振、滑らかなディケイ | フリーIR |
| Hall | 長いディケイ、広い空間 | フリーIR |
| Room | 短いディケイ、アーリーリフレクション | フリーIR |
| Spring | バネの共振音、独特のビヨン感 | フリーIR |
| Chamber | 石壁の反射、中程度のディケイ | フリーIR |

#### 処理フロー
```
音源 → GainNode(Dry) ──────────────┐
  └─→ ConvolverNode(IR_A) → Gain(Wet) → MergeA → Output A
                                        │
音源 → GainNode(Dry) ──────────────┐
  └─→ ConvolverNode(IR_B) → Gain(Wet) → MergeB → Output B
```

- Dry/Wet 比率は全問題で統一（例: Wet 30-40%）
- LUFSマッチングで音量差による判別を排除（MuComp実装を流用）

### Phase 2: アルゴリズミック版（将来）

IR版で検証後、DSPリバーブ実装に移行。

- Plate: Dattorro アルゴリズム
- Hall: FDN（Feedback Delay Network）
- Room: アーリーリフレクション + 短いFDN

追加ゲームモード候補:
- **「合わせろ」モード**: お手本のリバーブ感にDry/Wetやディケイを自分で調整して近づける（HORSE方式）
- **「量を当てろ」モード**: 同じリバーブタイプでDry/Wet比率の違いを当てる

## UI設計

### MuComp / MuFreQ との統一

```
┌──────────────────────────┐
│     🦉 MuVerb            │
│                          │
│   「Plateはどっち？」      │
│                          │
│  ┌─────┐    ┌─────┐     │
│  │ ▶ A │    │ ▶ B │     │
│  └─────┘    └─────┘     │
│                          │
│  ┌─────┐    ┌─────┐     │
│  │  A  │    │  B  │     │
│  └─────┘    └─────┘     │
│                          │
│   Score: 7/10            │
└──────────────────────────┘
```

- A/B 再生ボタン → 何度でも切り替えて聴ける
- 回答ボタンで選択
- 正解時: リバーブタイプの簡単な説明を表示
  - 例:「Plate — 金属板の振動を利用したリバーブ。滑らかで明るい響きが特徴」

### 設定画面
- 難易度選択（Easy / Medium / Hard）
- ラウンド数（5 / 10 / 20）
- リバーブ Wet 量の調整（上級者向け: Wet を下げるほど判別困難）

## 実装ステップ

### Step 1: UIリファクタ
- 現行の「3択で種類同定」UIを「A/B 2択比較」UIに変更
- MuComp の再生コンポーネントを流用

### Step 2: 出題ロジック
- ペアテーブル定義（Level 1-3）
- ランダム出題 + 正解位置のランダム化（A/Bどちらが正解か）
- 難易度に応じたペア選択

### Step 3: IR素材の整備
- 各タイプの代表的なフリーIRを選定
- Dry/Wet 固定で LUFSマッチング適用
- Spring IR の追加（現行にない場合）

### Step 4: フィードバック実装
- 正解時にリバーブタイプの解説を表示
- 「もう一度聴く」ボタンで復習可能

### 所要時間見積もり
- UI変更: 2-3時間
- 出題ロジック: 1-2時間
- IR素材整備: 1-2時間
- テスト・調整: 2-3時間
- **合計: 1日程度**
