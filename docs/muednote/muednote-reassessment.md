# MUEDnote 再評価 — 2026/02/20 議論まとめ

## 背景

SaaS・ソフトウェア産業の崩壊が始まっている。Anthropic CEOダリオ・アモデイの「ソフトウェアエンジニアリングは6〜12ヶ月以内にobsoleteになる」発言を起点に、SaaS企業の株価が半減。Capability（こうなる）からExecution（こうする）のフェーズに突入した。

この文脈でMUEDエコシステム全体を再評価した結果、以下の結論に至った。

---

## 結論

### MUEDnoteのアプリとしての存在意義がほぼ消失した。

理由：

1. **タイマー** → iOS標準の時計アプリで代替可能
2. **ボイスレコーダー** → iOS標準のボイスメモで代替可能
3. **文字起こし** → Claude/ChatGPT/Geminiに音声ファイルを投げれば完了。Whisper APIをアプリに内蔵する必然性が薄い
4. **Hooとの連携** → Hooがアプリ内に住む必要がない。外部からデータを読みに来る設計で十分
5. **認証（Clerk / Sign in with Apple）** → 上記全てにユーザーログインが不要。現在のリジェクト原因そのものが、存在しなくてよい機能

### MUEDnoteの本当の価値は「アプリ」ではなく「判断ログの蓄積」だった

- 「なぜその音を選んだか」という意思決定の記録
- これはnote記事群（https://note.com/mued_glasswerks/m/mf93ba6eeb58a）が既に実現している
- アプリに閉じ込める必要がない

---

## 重要な補足：今回の議論はiOSアプリに限定した話

MUEDnoteにはもう一つ、**macOS用のDAWログアプリ**が存在する。こちらはiOSアプリとは真逆で、**価値が増す側**にいる。

### なぜDAWログアプリは生き残るか

- Logic Pro/Ableton Live等の操作履歴を自動取得する（プラグイン変更、EQ設定、トラック操作等）
- これは「制作判断の自動記録」であり、AIに代替できない一次情報
- ユーザーが意識的にメモを取らなくても、制作行為そのものから判断の痕跡が抽出される
- Hooが参照すべきコンテキストとして、ボイスメモより圧倒的に情報密度が高い

### UIからAPI/MCPへの移行が加速している

以前から議論していた「UIそのものが意味をなくし、MCP/APIの接続層だけが残る」という予測が、MUEDnoteのiOS陳腐化を通じてリアルタイムで実証されている。

残るものの姿：
- **MUEDear** → UIが必要な例外（音を聴く体験はAPIにならない）
- **DAWログ（macOS）** → UIは最小限。DAWからデータを吸い上げるバックグラウンドプロセス＋MCP/API
- **MCP/API層** → HooやClaude等のAIが制作データを読みに来る接点
- **note記事** → 人間が読む一次情報

iOSアプリのUI構築→審査→ダウンロード→起動というプロセス全体が、MCP接続一本に置き換わりつつある。

| プロダクト | 判定 | 理由 |
|-----------|------|------|
| **MUEDear** | ✅ 生存・主役 | DSP自前実装。アプリである必然性がある。AIに代替不可（身体スキル訓練） |
| **DAWログ（macOS）** | ✅ 生存・主役 | 制作判断の自動記録。一次情報の自動蓄積装置。Hooが参照する最も価値の高いデータソース |
| **note記事群** | ✅ 生存・主役 | 一次情報。AIO経由の流入。AIに生成不可 |
| **MCP/API層** | ✅ 生存・基盤 | UIに代わる接続層。Hoo/Claude等がMUEDのデータを読みに来る接点 |
| **MUEDnote（iOS）** | ⚠️ 縮小 | 機能がOS標準+汎用AIに吸収される。無料で残すか、リソース投下を停止 |
| **MUEDlobe** | ⚠️ 優先度最低 | AIの自己適応能力に吸収される見込み |
| **Hoo** | ✅ 生存 | ただしアプリ内ではなく、Web/API/MCP経由で存在すればよい |
| **mued.jp** | ✅ ハブ | 上記を束ねる導線 |

## MUEDnote（iOS）の方針：確定

### 設計思想の転換

MUEDnote iOSアプリは「プロダクト」ではなく「MUEDエコシステムの名刺」として再定義する。
App Storeの中に存在するMUEDの入口。維持コストゼロで、エコシステム全体への導線を担う。

### 残す機能（ローカルオンリー・認証なし・サーバーなし）

1. **ポモドーロタイマー** — 今あるものをそのまま残す
2. **ボイスレコーダー** — 録音＋ローカル保存。書き起こしは後回しまたは不要
3. **メモ** — ローカル保存のシンプルなメモ

### 削除する機能

- **Clerk / Sign in with Apple / 認証全般** — リジェクト原因の根本解消
- **サーバーサイド連携** — バックエンド不要
- **Hooとのアプリ内チャット** — Hooはアプリの外（Web/MCP）に存在すればよい
- **課金・サブスク** — 無料ユーティリティとして配布

### 追加する役割：エコシステムへの導線ハブ

- **アプリ内ブログ記事** — 既存のコンテンツ（ポモドーロの語源、制作と休憩の関係等）を維持
- **note記事へのリンク** — ブログ記事の延長線上にnote記事群へ誘導（https://note.com/mued_glasswerks/）
- **mued.jp LPへのリンク** — MUEDの全体像を見せる導線
- **MUEDearへの誘導** — App Storeページへのリンク。「耳も鍛えたいならこっち」

### この設計の意図

- アプリ自体は完全スタンドアロンの無料ユーティリティ
- しかしコンテンツの中にMUEDエコシステム全体への動線が埋まっている
- 「アプリがなくなる時代」への移行期間に、MUEDの入口として静かに存在する
- 維持コストゼロ。審査で突っ込まれる要素がほぼない
- いずれiOSアプリの役割が完全に消えても、失うものがない設計

## 求める判断

MUEDnote（iOS）の方針は上記で確定。以下についてClaude Codeとしての技術的な判断・提案を求めます：

### MUEDnote（iOS）改修
1. Clerk/認証を完全に外し、ローカルオンリーにする場合の影響範囲と工数
2. 現在のコードベースからどこまで削ぎ落とせるか（削除対象の具体的なファイル・モジュール）
3. アプリ内ブログ記事→note記事→mued.jp→MUEDearへの導線設計で技術的に考慮すべき点

### エコシステム全体
4. macOS DAWログアプリの現状と、MCP/API層として設計する場合のアーキテクチャ案
5. 「UIが消えてAPI/MCPだけ残る」という方向に進む場合、現在のコードベースで何を残し何を捨てるべきか
6. MUEDearの開発にリソースを集中させる場合、MUEDnoteのコードベースで流用できる部分はあるか
7. その他、技術的観点からの意見

### 重要：設計がブレないための指針
この文書の方針は、以下の議論から導出されている：
- SaaS/アプリの陳腐化（機能はOS標準+汎用AIに吸収される）
- 残るのは「一次情報の蓄積」と「身体スキル訓練」と「API/MCP接続層」のみ
- MUEDnote（iOS）は「プロダクト」ではなく「エコシステムの名刺＋導線ハブ」
- 判断に迷った場合は「その機能にユーザー認証が必要か？」を問い、不要なら削る方向で進める
